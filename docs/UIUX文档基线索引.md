# 需求审查与 UI/UX 文档基线索引

状态：第一批文档基线

适用范围：需求审查、业务规则核对、信息架构与 UI/UX 设计评审

目标分支：`docs/uiux-baseline`

本索引说明第一批文档的用途、权威性、阅读顺序和已知冲突。纳入本索引不等于批准文档中的所有方案；标记为“待确认”的内容不得自动升级为正式需求、开发任务或验收条件。

## 一、权威性与阅读优先级

按以下顺序阅读和处理冲突：

1. `docs/需求基线_TAPD对齐版_V1.0.md`：本仓库中的现行需求入口；产品范围、优先级、用户故事和验收标准以该文档及 TAPD 已确认记录为准。
2. `CONTEXT.md`：统一业务术语和领域概念，不得据此扩大需求范围。
3. `docs/adr/`：约束架构、权限、历史数据和 AI 行为；涉及 AI 的 ADR 不表示本期必须建设 AI 功能。
4. `docs/design/`：用于信息架构、流程、页面和视觉评审；设计稿不得自动升级为正式需求。
5. `docs/architecture/`：用于理解技术边界、工程分层和待确认事项；文档中的目标方案不等于已经实现或验收通过。
6. `AGENTS.md` 与 `docs/agents/`：用于项目协作和代理工作约定，不构成业务需求。

发生冲突时，应记录问题并等待确认，不得仅按文件日期、版本号或完成度自行覆盖上级依据。

## 五、设计与需求边界

- 设计文档负责组织信息、表达交互和呈现视觉，不得创造需求基线中不存在的业务能力。
- 设计评审提出的范围调整、页面增删和默认规则，必须回到 TAPD 或需求基线完成确认后才能成为正式需求。
- 示例数据、界面文案和原型行为仅用于说明设计，不得作为真实经营数据或已确认业务结论。
- 后续设计评审应先阅读需求基线和领域术语，再阅读对应 ADR、信息架构、用户流程、页面清单及视觉规范。
