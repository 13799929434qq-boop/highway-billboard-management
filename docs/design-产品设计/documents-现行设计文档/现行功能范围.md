# 高速公路广告牌管理系统：现行功能评审

评审日期：2026-10-07  
权威范围：`docs/requirements-需求文档/需求基线_TAPD对齐版_V1.0.md`  
评审对象：P1～P8，共 8 个模块、46 个功能点  
范围约束：不增加招标、投标、保证金、公开门户、地图、在线支付等现行 PRD 未定义的功能。

## 一、评审结论

现行需求已经形成一条可成立的经营闭环：

> 账号授权 → 广告牌建档 → 客户建档 → 合同确认 → 生成应收 → 收款核销 → 经营报表 → 到期提醒与售后维护

八个模块的主体功能能够互相衔接，可以继续进行 UX 设计和分批开发。但目前有 **1 项范围问题、5 项关键规则待明确、4 项普通规则待确认**。这些问题不需要增加新模块，应在现有功能内部明确规则。

## 二、范围评审

### 已确认在范围内

| 模块 | 现行能力 |
| --- | --- |
| P1 账号与系统管理 | 登录、岗位权限、菜单/数据/按钮权限、数据字典、操作日志 |
| P2 广告牌资产 | 路段与归属、基本档案、三个桩号、三类手续、照片、查询、资产变动 |
| P3 客户 | 基本资料、开票信息、余额欠款、黑名单、客户合同与资金汇总 |
| P4 合同 | 新建、多广告牌、年度租金、租期冲突、状态、续签/变更/解除、附件 |
| P5 财务 | 年度应收、欠款、收款、部分核销、多账单核销、挂账、支出、发票 |
| P6 报表 | 数量、合同执行、收款、欠款、经营收益、Excel/PDF 导出 |
| P7 提醒 | 合同到期、欠费、证件到期、付款到期 |
| P8 售后 | 问题登记、处理进度、维修结果与费用 |

### 应从当前范围移除

**H-01 工作台（聚合待办、指标、风险、资产分布）**没有对应 TAPD 功能点和验收标准，却曾在信息架构和 MVP 页面清单中被列为 High。

处理建议：

- 当前不开发独立工作台。
- 用户登录后，按岗位直接进入已有的主要业务页面。
- 部门领导进入已有经营报表；系统管理员进入岗位与权限设置。
- 将来如果确实需要工作台，应先增加正式用户故事和验收标准。

## 三、模块评审

### P1 账号与系统管理：通过

优点：

- 登录错误、五次锁定、禁用账号、会话超时、退出失效均有明确标准。
- 菜单、数据和按钮三层权限定义清楚。
- 多岗位用户按权限并集显示，逻辑可执行。
- 系统管理员不自动获得业务数据权限，符合 ADR-0005。

需要保持的 UX：未授权菜单不显示；直接访问未授权 URL 时给出无权限页面；权限变化后重新登录生效。

### P2 广告牌资产管理：基本通过，1 项关键规则待明确

优点：

- 三个桩号、路政/保险/年审和现场照片体现了公路广告牌行业特点。
- 路段停用后不影响历史档案，处理合理。
- 拆除和移位保留前后记录，满足追溯要求。

关键问题：P2-07 写有“变动确认”和“驳回”，但没有规定由谁确认、状态如何流转、制单人能否自行确认。

评审结论：基本档案、查询和详情 UX 可继续；资产变动页面在确认角色明确前只能标记为“待确认”。

### P3 客户管理：通过，1 项普通规则待确认

优点：

- 客户资料、多个发票抬头、余额欠款、黑名单和合作记录形成完整客户视图。
- 已有生效合同的客户不能删除，只能停用，历史关系不会断裂。

普通问题：客户名称重复的判断规则未说明是否忽略空格、大小写、简称和统一社会信用代码。当前可以先按名称完全匹配实现，规则需由业务确认。

### P4 合同管理：主体通过，2 项关键规则待明确

优点：

- 一份合同关联多块广告牌，并允许分别设置租期和年度租金。
- 黑名单与租期冲突能够阻止合同生效。
- 草稿、待确认、生效、到期、解除状态及操作记录清楚。
- 制单人与确认人必须不同，内部控制合理。

关键问题：

1. 哪个现有岗位拥有“合同确认”权限没有确定。该权限可以配置，但必须给出默认责任岗位。
2. 生效合同变更租金或租期后，已有应收如何调整没有验收标准。ADR-0003 要求保留历史并使用调整记录，但现行页面和操作规则尚未定义。

评审结论：新建合同和首次确认流程可继续设计；合同变更涉及应收调整的部分暂不能定稿。

### P5 财务管理：主体通过，1 项关键规则待明确

优点：

- 应收与收款分离，实际收款不会因为尚未核销而消失。
- 支持部分核销、一笔收款核销多张账单和客户挂账。
- 支出台账与应收台账独立，财务事实边界清楚。

关键问题：发票“未开票金额”的计算口径没有明确。需要确认以应收金额、已核销金额还是实际收款金额作为开票上限和未开票基数。

普通问题：部分缴款自动分配顺序未定义。当前 UX 应让财务人员明确选择分配账单，不能自行假设先到期先核销。

### P6 经营统计报表：主体通过，1 项关键规则待明确

优点：

- 数量、合同、收款和欠款报表都能追溯至已有业务事实。
- Excel/PDF 按当前筛选导出，页面和文件口径一致。
- 部门领导只读，职责清楚。

关键问题：基线使用“经营收入、支出及净收益”，而统一业务语言规定应使用“经营收益测算”，不能等同于会计利润。需要固定计算公式、统计时间口径以及按应收还是现金计算。

建议沿用 `docs/domain-领域模型/CONTEXT-领域上下文.md` 中的定义：经营收益测算以统计期间租金应收减去已确认经营成本形成，并在报表页明确展示口径。

### P7 消息与到期提醒：逻辑通过，2 项普通规则待确认

优点：

- 四类提醒分别送达合同、财务和运营岗位。
- 付款临期转欠费，避免同一账单重复提醒。
- 已核销、已解除或草稿记录不会错误触发提醒。

待确认：

1. 合同、付款和证件分别提前多少天提醒。
2. 提醒天数由谁维护，以及修改后是否只影响后续提醒。

这属于现有提醒功能的参数，不需要新增模块。

### P8 售后维护：主体通过，1 项普通规则待确认

优点：

- 问题登记、分派、处理时间线、维修结果和关闭形成闭环。
- 问题与广告牌、照片、维修费用及财务应付建立关联。
- 关闭后不可修改，保留历史事实。

待确认：不同紧急程度分别允许多长处理时间，超时规则如何计算。该规则需要在现有售后功能内配置或固定。

## 四、跨模块闭环评审

| 闭环 | 结果 | 说明 |
| --- | --- | --- |
| 广告牌 → 合同 | 通过 | 合同关联整块广告牌，租期冲突阻止重复出租。 |
| 客户 → 合同 | 通过 | 黑名单阻止确认生效，客户资料可复用。 |
| 合同 → 应收 | 通过 | 生效后按广告牌、计费年度生成应收。 |
| 收款 → 核销 → 欠款 | 通过 | 独立收款流水支持部分、多账单和挂账。 |
| 支出/维修 → 报表 | 条件通过 | 维修费用生成应付；经营收益口径仍需固定。 |
| 证件/合同/账单 → 提醒 | 条件通过 | 触发逻辑完整，提前天数待确认。 |
| 权限 → 页面/数据/按钮 | 通过 | 六类岗位共用系统骨架，权限决定可见范围。 |

## 五、UX 评审结论

当前确认的 UX 原则可以继续使用：

1. 不为六类岗位分别开发六套界面，使用统一页面骨架和权限控制。
2. 不使用没有实际任务的角色首页，登录后进入岗位主要页面。
3. 列表用于查找，快速详情用于核对，完整详情用于查看全部资料和历史。
4. 表单错误显示在对应字段旁，保存失败保留已填写内容。
5. 加载、无数据、无权限、失败和成功必须有独立状态与恢复动作。
6. 状态不能只靠颜色表达，必须配合清晰文字。

已经完成 UX 布局评审的范围：广告牌列表、快速详情、完整档案、新建/编辑和关键异常状态。

尚未完成 UX 布局评审的现行页面：登录与权限、路段维护、广告牌变动、客户、合同、财务、报表、提醒和售后。

## 六、问题优先级

### P0：立即纠正范围

- 移除没有 TAPD 用户故事的独立工作台，不纳入当前开发。

### P1：进入对应页面设计前必须明确

1. 广告牌拆除/移位的确认人和状态流转。
2. 合同确认权限默认属于哪个现有岗位。
3. 生效合同变更后如何形成应收调整。
4. 发票未开票金额采用什么口径。
5. 经营收益测算的公式和时间口径。

### P2：可在页面标记待确认

1. 客户重复名称判定规则。
2. 部分缴款的默认分配顺序。
3. 各类提醒提前天数及维护责任人。
4. 售后问题超时阈值。

## 七、最终判断

现行 46 个功能点总体合理，核心经营链条完整。当前应继续评审和设计现有模块，不需要增加新功能。

在 P1 规则没有确认前，可以完成列表、详情和基础表单布局，但不能把相关状态流转、计算结果或权限行为当作最终方案。
