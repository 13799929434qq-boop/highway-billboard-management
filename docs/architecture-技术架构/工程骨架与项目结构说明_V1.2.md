拆仓触发条件不变。

## 三、后端目标结构与分层

```
backend/app/
├─ main.py · core/ · db/ · models/ · schemas/
├─ repositories/  # 按需，阶段三
├─ services/      # 业务规则、事务边界
├─ api/v1/ · dependencies/
```

- 依赖方向：**api → service → repository → models**。
- Repository 按需引入（复杂模块优先），简单 CRUD 不强行建。
- 事务边界在 Service；合同计价/核销与普通 CRUD 分文件，避免巨型 service。

## 四、前端目标结构与分层

```
frontend/src/
├─ router/ · stores/ · api/ · views/（按 P1~P8）
├─ components/ · composables/ · utils/ · assets/ · styles/
```

- 按钮指令只控制展示，**不是安全边界**，以后端校验为准；组件库建议 Element Plus（或 UI 定）。

## 五、API 契约规范

- RESTful，前缀 `/api/v1`，JSON；破坏性变更升版本号。
- 成功响应：`{ code:0, message:"success", data }`；分页 `data={items,total,page,page_size}`；排序 `sort=field` / `sort=-field`。
- HTTP 状态码与**错误码类别**（V1.2：现阶段仅分类，`x` 为占位，**阶段二固化最小错误码表**）：

| HTTP | 场景 | 错误码类别 |
|---|---|---|
| 400 | 业务规则不满足 | 4xxx |
| 401 | 未登录/会话失效 | **401x（类别，阶段二细化）** |
| 403 | 无权限 | **403x（类别）** |
| 404 | 不存在 | 404x |
| 409 | 冲突 | 409x |
| 422 | 参数校验失败 | **422x（类别）** |
| 500 | 服务端错误 | 500x |

- 422 统一格式：`{ code, message, data:{ errors:[{field,message}] } }`。
- 上传 `multipart/form-data`；下载走文件流、错误回统一 JSON。
- **OpenAPI Schema 是前后端契约**；Swagger `/docs` 仅参考，不替代接口设计。

## 六、认证与会话安全

- 服务端不透明会话 + `Secure、HttpOnly、SameSite=Lax` Cookie；会话态存 Redis，30 分钟滑动空闲超时。
- 密码 Argon2id；不存在账号执行等价伪校验，统一"用户名或密码错误"，防枚举。
- 登录成功后**轮换 Session ID**；修改状态的请求做 **CSRF 防护**；生产 Cookie 仅经 HTTPS。
- Redis 不可用 **fail-closed**；账号安全事实存 MySQL，第 5 次失败原子锁定一次。
- 服务端鉴权为最终边界；受保护页禁缓存；遵守 ADR-0005。
- **【V1.2，阶段二必须验证】** 跨站部署下 Cookie 生效条件：前后端/正式域名关系、SameSite 取值、CSRF Token 跨域携带与 Secure 要求；未验证通过不进入正式使用。

## 七、数据库与迁移

- SQLAlchemy 2.x；Alembic 管理表结构，变更必须提交迁移脚本。
- 命名蛇形、模块前缀、`id`、`created_at/updated_at`。
- 种子数据：字典项、初始管理员（受控初始化，禁止固定密码）。
- **阶段一仅初始化 Alembic 迁移环境，不执行 `upgrade`、不生成业务表迁移**（见最小清单 B6）。

## 八、事务一致性规范

- 合同生效（锁定时段+生成应收）、收款核销（冲应收+写流水+更新余额）在单事务内完成，失败回滚。
- 遵循 ADR-0003：生效后不覆盖历史，变更走调整单，已核销不删除。

## 九、配置与环境

- pydantic-settings 读 `.env`；dev/prod 分离；提供 `.env.example`，密钥不入库。
- 安全数值（5 次、15 分钟、30 分钟）为**拟定默认值，可配置、待甲方确认**，不硬编码、**不自动成为正式需求**。
- docker-compose 分阶段、非阶段一必须。

## 十、代码规范

- 前端 ESLint + Prettier；后端 Ruff + Black；Conventional Commits；PR 模板、分支 `feature/p1-01-xxx`。

## 十一、测试体系

| 层次 | 工具 | 引入时机 |
|---|---|---|
| 前端单元 | Vitest | 阶段一接入入口 |
| 后端单元 | pytest | 已有，持续补充 |
| API 集成 | pytest + httpx | 阶段二 |
| E2E | Playwright | 有闭环后，先登录+核心闭环 |
| 契约检查 | OpenAPI | 契约定稿后 |

- 金额、核销、越权、状态流转为重点；CI 先做"构建+测试"最小流水线，不首轮铺满。

## 十二、需求追踪链

`TAPD（P1-01）→ 分支 feature/p1-01-login → PR（测试+评审）→ 合并 main → 更新 TAPD 状态`；证据回填追踪矩阵；分支/PR 带 TAPD 标识。

## 十三、部署架构（ADR-0001）

- 前期 Vercel + 云后端（注意 Python Runtime Beta 风险）；正式前迁阿里云 OSS+CDN / Docker ECS / 内网 RDS、Redis、OSS。
- Milvus/AI 为可选/后续（ADR-0002），不纳入本期核心。
- **阶段二必须在接近正式域名的环境验证 Cookie/SameSite/CSRF（见第六章）。**

## 十四、骨架落地三阶段

| 阶段 | 内容 | 准入/产出 |
|---|---|---|
| **阶段一 工程初始化** | 启动验证、**只建当前使用目录**、依赖锁定、`.env.example`、ESLint/Ruff、测试入口、**Alembic 仅初始化**、Git/TAPD 规范 | 前后端可启动、规范生效 |
| **阶段二 基础设施** | 数据库连接、迁移基线、Redis、统一响应/异常、认证安全底座、**跨站 Cookie/SameSite/CSRF/域名验证**、最小 CI、**固化最小错误码表** | 认证在真实依赖上运行 |
| **阶段三 需求驱动开发** | 按 TAPD 垂直切片；Repository/E2E/契约/完整 CI/Docker 按需 | 每切片可演示验收 |

> 不预生成空目录、占位文件或用不到的抽象层。
