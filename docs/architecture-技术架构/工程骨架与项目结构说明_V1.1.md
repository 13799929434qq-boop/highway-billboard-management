## 三、后端目标结构与分层【V1.1 增 Repository 与事务边界】

```
backend/app/
├─ main.py
├─ core/          # config、security、exceptions
├─ db/            # engine、session、base
├─ models/        # SQLAlchemy 模型
├─ schemas/       # Pydantic 出入参
├─ repositories/  # 【V1.1，按需】数据访问与持久化
├─ services/      # 业务规则、流程编排、【事务边界在此】
├─ api/v1/        # 路由
└─ dependencies/  # 鉴权、权限、分页
```

- **依赖方向：api → service → repository → models**；不允许反向依赖、不允许路由直接写复杂业务。
- **Repository 按需引入**：合同、财务等复杂模块优先；简单 CRUD 可直接用 model，**不为每张表强行建 Repository**。
- **事务边界在 Service 层**：合同生效、收款核销等跨表操作在一个事务内提交，失败整体回滚（详见第八章）。
- 合同计价、财务核销等核心规则与普通 CRUD 分文件组织，避免出现数千行的 `services/contract.py`。

## 四、前端目标结构与分层（沿用，补权限落点）

```
frontend/src/
```

## 五、API 契约规范【V1.1 大幅补充】

- RESTful，前缀 `/api/v1`，JSON；版本升级保持向后兼容，破坏性变更升版本号。
- 统一成功响应：`{ "code": 0, "message": "success", "data": ... }`。
- 分页：请求 `page`、`page_size`；响应 `data = { items, total, page, page_size }`。
- 筛选/排序统一命名：筛选字段直命名；排序 `sort=field` / `sort=-field`（- 为降序）。
- **HTTP 状态码与业务码映射：**

| HTTP | 场景 | 业务 code |
|---|---|---|
| 200 | 成功 | 0 |
| 400 | 业务规则不满足 | 4xxx |
| 401 | 未登录/会话失效 | 401x |
| 403 | 已登录但无权限 | 403x |
| 404 | 资源不存在 | 404x |
| 409 | 冲突（如重复出租） | 409x |
| 422 | 参数校验失败 | 422x |
| 500 | 服务端错误 | 500x |

- **422 统一格式**：Pydantic 校验失败返回 `{ code:422x, message, data:{ errors:[{field,message}] } }`。
- 文件上传走 `multipart/form-data`；下载/导出返回文件流，错误时仍回统一 JSON。
- **OpenAPI Schema 是前后端接口契约**，纳入评审；Swagger `/docs` 只是自动生成的参考，不替代接口设计与业务规则说明。

## 六、认证与会话安全【V1.1 对齐 OpenSpec design 并补轮换】

- 服务端不透明会话 + `Secure、HttpOnly、SameSite=Lax` Cookie；会话运行态存 Redis，设 30 分钟滑动空闲超时。
- **密码 Argon2id 哈希**（带独立盐）；不存在账号也执行等价成本伪校验，统一返回"用户名或密码错误"，防账号枚举与时间侧信道。
- 【V1.1 新增】**登录成功后轮换 Session ID**，降低会话固定攻击风险。
- **CSRF 防护**：修改状态的请求除 SameSite 外，校验 CSRF Token / 来源。
- **生产环境 Cookie 仅经 HTTPS（Secure）**；开发环境显式配置本地替代，不自动放宽生产策略。
- **Redis 不可用时 fail-closed**：健康检查暴露依赖状态，认证安全关闭、不绕过；Redis 丢失只使会话失效，不解锁账号、不改状态。
- 账号安全事实（失败次数、锁定状态）存 MySQL，用事务与原子更新保证第 5 次失败只锁定一次。
- **服务端鉴权是最终边界**，所有业务路由默认要求有效会话；前端守卫/隐藏按钮仅改善体验。
- 受保护页面禁止缓存，避免退出后回退显示旧数据。
- 遵守 ADR-0005：系统管理员不自动获得业务数据访问权。

## 七、数据库与迁移（沿用，补充）

- SQLAlchemy 2.x 模型；Alembic 管理表结构，升级/回滚可追溯；表结构变更必须提交迁移脚本，禁止手改库不记录。
- 命名：蛇形小写、模块前缀、主键 `id`、时间 `created_at/updated_at`。
- 种子数据脚本：数据字典项、初始管理员（受控初始化，禁止内置固定密码）。

## 八、事务一致性规范【V1.1 新增】

- 合同生效（锁定广告牌时段 + 生成应收）、收款核销（冲应收 + 写流水 + 更新余额）等跨表操作必须在单事务内完成，失败回滚。
- 遵循 ADR-0003：合同/资金生效后不覆盖历史，变更走调整单，收款/退款独立记录，已核销数据不删除。

## 九、配置与环境（沿用，补交付模板）

- pydantic-settings 读 `.env`；dev/prod 分离；**提供 `.env.example`**，密钥与连接串不入库。
- 业务安全数值（连续错 5 次、锁定 15 分钟、超时 30 分钟）为**团队拟定默认值，可配置、待甲方确认**，不硬编码。
- 【V1.1，分阶段】本地/测试可用 `docker-compose.yml` 提供 MySQL+Redis；非本阶段必须。

## 十、代码规范（沿用）

- 前端 ESLint + Prettier；后端 Ruff + Black；保存自动格式化。
- 命名与提交规范：Conventional Commits（`feat/fix/docs/refactor/test/chore: 描述`）；提供 **PR 模板**与分支命名 `feature/p1-01-login`。

## 十一、测试体系【V1.1 补分层，基础设施先行】

| 层次 | 工具 | 内容 | 引入时机 |
|---|---|---|---|
| 前端单元 | Vitest | 工具/组件 | 初始化阶段接入入口 |
| 后端单元 | pytest | 业务规则、金额计算 | 已有，持续补充 |
| API 集成 | pytest + httpx | 路由+数据库+权限 | 基础设施阶段 |
| E2E | Playwright | 登录→核心业务闭环 | 有可运行闭环后，先做登录+闭环 |
| 契约检查 | OpenAPI | 前后端一致性 | 接口契约定稿后 |

- 金额计算、缴款核销、越权、状态流转列为重点自动化对象；**首日不写满，但测试基础设施在初始化阶段确定**。
- CI【V1.1，分阶段】：先做"构建 + 测试通过"最小流水线，再逐步加入契约/E2E，不首轮铺满。

## 十二、需求追踪链【V1.1 新增】

`TAPD 需求（P1-01）→ Git 分支 feature/p1-01-login → PR（自动测试 + 评审）→ 合并 main → 更新 TAPD 状态`；测试证据回填需求追踪矩阵。分支名、PR 必须带 TAPD 标识。

## 十三、部署架构（沿用 ADR-0001）

- 前期：前端 Vercel + 后端/数据库上云（低运维、快速迭代，注意 Vercel Python Runtime 的 Beta 风险）。
- 正式使用前：前端阿里云 OSS+CDN，后端 Docker 部署 ECS，内网连 RDS MySQL、Redis、OSS。
- ADR-0001 提及的 Milvus/AI 能力属**可选/后续**，遵循 ADR-0002（AI 仅建议、不直接改业务数据），**不纳入本期核心范围**。
- 发布前过构建/测试/迁移，准备回滚；服务器、域名等资源由甲方提前准备。

## 十四、骨架落地路线【V1.1 由"一次全量"改为三阶段】

| 阶段 | 内容 | 产出/准入 |
|---|---|---|
