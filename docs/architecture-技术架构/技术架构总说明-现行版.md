├─ backend/    # 独立依赖、构建、测试和部署

## 三、后端目标结构与分层

```text
backend/app/
├─ main.py
├─ core/
├─ db/
├─ models/
├─ schemas/
├─ repositories/  # 按需引入，阶段三
├─ services/      # 业务规则和事务边界
├─ api/v1/
└─ dependencies/
```

- 依赖方向：**api → service → repository → models**。
- Repository 按需引入，复杂模块优先，简单 CRUD 不强制建立。
- 事务边界放在 Service；合同计价、核销与普通 CRUD 分文件，避免巨型 Service。

## 五、API 契约规范

- 使用 RESTful 风格，统一前缀 `/api/v1`，数据格式为 JSON；破坏性变更升级 API 版本号。
- 成功响应：`{ code: 0, message: "success", data }`。
- 分页响应：`data = { items, total, page, page_size }`。
- 排序参数：`sort=field` 或 `sort=-field`。

| HTTP | 场景 | 错误码类别 |
|---|---|---|
| 400 | 业务规则不满足 | 4xxx |
| 401 | 未登录或会话失效 | 401x |
| 403 | 无权限 | 403x |
| 404 | 资源不存在 | 404x |
| 409 | 数据冲突 | 409x |
| 422 | 参数校验失败 | 422x |
| 500 | 服务端错误 | 500x |

当前只确定错误码类别，`x` 为占位符；阶段二再固化最小错误码表。

- 422 统一格式：`{ code, message, data: { errors: [{ field, message }] } }`。
- 上传使用 `multipart/form-data`；下载使用文件流，错误仍返回统一 JSON。
- OpenAPI Schema 是前后端契约；Swagger `/docs` 仅用于查看，不代替接口设计。

## 六、认证与会话安全

- 使用服务端不透明会话，以及 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie；会话状态存入 Redis，拟定为 30 分钟滑动空闲超时。
- 密码使用 Argon2id；不存在的账号执行等价伪校验，统一返回“用户名或密码错误”，防止账号枚举。
- 登录成功后轮换 Session ID；修改状态的请求进行 CSRF 防护；生产 Cookie 只允许通过 HTTPS 传输。
- Redis 不可用时采用 fail-closed；账号安全事实保存在 MySQL，拟定为第 5 次失败时原子锁定一次。
- 服务端鉴权是最终安全边界；受保护页面禁止缓存，并遵守架构决策总表中的数据权限规则。
- 阶段二必须验证跨站部署下的正式域名关系、SameSite 取值、CSRF Token 跨域携带与 Secure 要求；未验证通过不得进入正式使用。

## 七、数据库与迁移

- 使用 SQLAlchemy 2.x；Alembic 管理表结构，结构变更必须提交迁移脚本。
- 数据库命名使用蛇形命名、模块前缀，并包含 `id`、`created_at`、`updated_at`。
- 种子数据包括字典项和初始管理员；必须通过受控流程初始化，禁止固定密码。
- 阶段一只初始化 Alembic 迁移环境，不执行 `upgrade`，不生成业务表迁移。

## 八、事务一致性

- 合同生效时，锁定时段和生成应收必须在同一事务内完成。
- 收款核销时，冲减应收、写入流水和更新余额必须在同一事务内完成。
- 任一步骤失败时整体回滚。
- 生效后的合同和资金记录不得覆盖历史；变更通过调整记录完成，已经核销的数据不得删除。

## 九、配置与环境

- 使用 pydantic-settings 读取 `.env`，开发与生产环境分离。
- 提供 `.env.example`，不得将真实密钥提交到仓库。
- “失败 5 次、锁定 15 分钟、空闲 30 分钟”都是可配置的拟定默认值，甲方确认前不得作为正式需求写死。
- Docker Compose 按阶段引入，不是阶段一必需项。

## 十、代码与协作规范

- 前端使用 ESLint 和 Prettier。
- 后端使用 Ruff，Black 为可选。
- Git 提交使用 Conventional Commits。
- 使用 PR 模板，功能分支格式为 `feature/p1-01-xxx`。

## 十一、测试体系

| 层次 | 工具 | 引入时机 |
|---|---|---|
| 前端单元测试 | Vitest | 阶段一接入入口 |
| 后端单元测试 | pytest | 已有，持续补充 |
| API 集成测试 | pytest + httpx | 阶段二 |
| 端到端测试 | Playwright | 形成业务闭环后，先覆盖登录和核心闭环 |
| 契约检查 | OpenAPI | 契约定稿后 |

金额、核销、越权和状态流转是测试重点。CI 先建立“构建 + 测试”的最小流水线，不在首轮铺满。

## 十二、需求追踪链

`TAPD（P1-01）→ 分支 feature/p1-01-login → PR（测试与评审）→ 合并 main → 更新 TAPD 状态`

证据需要回填追踪矩阵，分支和 PR 必须带 TAPD 标识。

## 十三、部署架构

- 个人开发和试用阶段采用 Vercel 与云后端，注意 Vercel Python Runtime 的 Beta 风险。
- 正式使用前迁移至阿里云 OSS + CDN、Docker ECS，以及内网 RDS、Redis 和 OSS。
- Milvus 和 AI 属于可选或后续能力，不纳入当前核心范围。
- 阶段二必须在接近正式域名的环境验证 Cookie、SameSite 和 CSRF。

## 十四、分阶段落地路线

| 阶段 | 内容 | 准入或产出 |
|---|---|---|
| 阶段一：工程初始化 | 启动验证、只建当前使用目录、依赖锁定、`.env.example`、ESLint/Ruff、测试入口、Alembic 仅初始化、Git/TAPD 规范 | 前后端可启动，规范生效 |
